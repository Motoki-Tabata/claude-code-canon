# context 軸 判定: ctx-bloat

## 対象
- `.claude/skills/use-logger/SKILL.md`（design-map の1文責務: 「構造化ロガーの使い方（1点）」）

## 判定

### 重複（複数ファイルに同一内容）
バンドルに含まれる target は本ファイル1点のみで、比較対象となる他ファイルが与えられていない。
そのため「同じ内容が複数ファイルに書かれ、更新時に片方が腐る」構造の有無は、与えられた材料からは
確認できない。この観点については violation の根拠がないため clean とする（ただし他ファイルとの
突合は行っていない点を明記する）。

### 読まれない冗長・責務の肥大
本文（29〜42行目相当）を分解すると次の通り:

- 実効的な指示は最終段落の2行のみ:
  「`import { log } from 'src/log'` して `log.info(msg, ctx)` を使う。エラーは `log.error(err)`。
  `console.log` は使わない。」——これが「構造化ロガーの使い方」という1文責務そのもの。
- それに先立つ2段落（本文中の該当箇所）が、実効的な指示を含まない一般論・自明な注意書きで
  占められている:
  - 1段落目: 「ロギングは非常に重要です」「ログが多すぎるとノイズになり、少なすぎると調査が
    できません」「バランスが大切です」「ログはチームの共有資産」「読みやすいログは価値があり、
    読みにくいログは負債になります」「ログレベルには意味があり、正しく使い分けることが望まれます」
    「ロギングの文化はチームで育てるものです」——いずれもロギング全般に関する一般論で、
    「どのライブラリをどう呼ぶか」という判断には一切寄与しない。specific な API 名も規約名も
    出てこない。
  - 2段落目: 「ログは重要なので、丁寧に扱いましょう」「出力先や書式はプロジェクトごとに異なる
    場合があるため、状況に応じて判断してください」「エラーは記録すべきです」——これも同様に
    自明かつ非実効的。「状況に応じて判断してください」は判断基準を何も与えておらず、実質的に
    何も言っていない一文。
- 分量比で見ると、非実効的な一般論が2段落（実質9行程度）を占め、実効的な指示はわずか2行。
  この skill は `description: Use when adding log output.` として都度呼び出される想定であり、
  呼び出されるたびにこの一般論を読み込むコストが発生する。BEST_PRACTICES.md §1.1
  「コンテキストは最も貴重な資源」の趣旨に照らし、実効的な指示（2行）が非実効的な一般論
  （9行前後）に埋もれている状態は「読まれない冗長」に該当する。
- 一方、内容が design-map の1文責務（「構造化ロガーの使い方」）の外側の別責務（例: ログ基盤の
  設計方針、監視体制、ログレベルのプロジェクト固有ルール策定など）にまで実質的に踏み込んで
  いるわけではない。一般論は抽象的な精神論に留まっており、具体的な別責務を担ってはいない。
  したがって「責務の肥大」というより「同じ1責務の中で、実効性のない説明文が実効的な指示の
  分量を上回っている」冗長性の問題として捉えるのが妥当。

## 結論
- 重複: 判定材料不足のため clean（他ファイルとの比較ができないため violation の根拠なし）。
- 読まれない冗長: violation（confidence: high）。実効的な指示2行に対し、判断に使われない
  一般論・自明な注意書きが数倍の分量で先行しており、都度読み込まれるコストに見合わない。
