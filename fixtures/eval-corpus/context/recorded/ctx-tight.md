# context 軸 判定結果: ctx-tight

## 対象
- `.claude/skills/hotfix-flow/SKILL.md`（バンドル `ctx-tight` に含まれる唯一の target）

## 判定

### 重複
バンドルに含まれる生成物は本ファイル1件のみで、比較対象となる他ファイルが存在しない。
同一内容が複数ファイルに分散して「更新時に片方が腐る」構造は、この入力からは確認できない
（そもそも構造上発生しえない）。重複なし。

### 読まれない冗長・責務の肥大
本文は frontmatter（`name` / `description`）＋見出し＋4行の手順のみで構成される。

1. `main` から `hotfix/<要約>` を切る。
2. 修正＋回帰テストを1コミットにまとめる。
3. PR を出し、レビュー1名で承認後に `main` へ。
4. タグを打ち本番へ配信。反映後にスモークで確認する。

各行はいずれも実行順序上必要な意思決定点（ブランチ命名規則／コミット粒度／レビュー要件／
リリース後の確認手段）を過不足なく1行で述べており、判断に使われない説明・自明な注意書き
（例:「バグは早く直しましょう」等の説教的記述）や重複した言い回しは存在しない。

design-map の1文責務は「hotfix ブランチの切り方と本番反映の手順」。実体の4行は
(1)(2) がブランチの切り方〜変更のまとめ方、(3)(4) が本番反映（レビュー・マージ・タグ・配信・
スモーク確認）に対応しており、1文責務の範囲に収まっている。ロールバック手順・障害対応の
エスカレーション・恒久修正へのフォローアップ等、1文責務が言及していない別責務への越境は
見当たらない。責務の肥大なし。

### 総評
4行という分量そのものは「短い」だけであり、それを冗長・不足と読み替える理由はない。
むしろ preload コストや反復読解コストの観点では望ましい密度であり、本バンドルにおいて
指摘すべきコンテキスト効率上の欠陥は見当たらない。
