## S1-1. `parseSystemA()` が `path` キーを行末まで取り込み、G2 の keep 判定が機構的に成立しない

**前回 S1-2 の再発。ただし原因が違う。前回の推奨は実装済みで、その先で別の壁に当たった。**

**前回の推奨と、その実装状況（実測）**:

| 前回の推奨 | 今回の状況 |
|---|---|
| ① `existing-customization-analyzer` の出力に `canon_conformance` と `depends_on.project_refs` を必須フィールドで持たせる | **実装済み**。`work/20260910_220906/existing_customizations.md` に `canon_conformance` が29回（＝全レコード）出現する |
| ② `project-profiler` の focused モードに `ref_resolution` 節を必須にする | **実装済み**。`project_profile.md` の `## focused` に `ref_resolution` 35件が出力され、G1 が実在照合して通過した |

**それでも keep は0件になった。**

**症状**: designer が29レコードすべてを keep にできず、初回の design-map は
`keep 0 / modify 28 / out_of_scope 1` になった。**実体判断では C1〜C5 をすべて満たす
`.claude/settings.json` と `.mcp.json` の2件も keep にできなかった。** 帰結として
**G8 の sha256 バイト同一照合が1件も走らない**。前回とまったく同じ「非回帰担保の喪失」である。

**原因**: `gates/lib/investigation.js` の `parseSystemA()`。

```js
const pathM = line.match(/^\s*-\s*path:\s*(.+?)\s*$/);
```

`(.+?)` は非貪欲だが **`$` アンカーがあるため結局行末まで取り込む**。系統A がレコード見出しを

```
- path: .claude/settings.json / layer: L5 / kind: settings / strength: mandatory（…）
```

の**1行形式**で書いていたため、`records` のキーが
`.claude/settings.json / layer: L5 / kind: settings / strength: mandatory（…）` になった。
`gates/g2_keep_judgement.js` は `sysA.get(r.path)`（`r.path` = `.claude/settings.json`）で引くので
**必ず undefined** になり、`G2: keep "<path>" が系統A に無く C1/C3/C5 を実照合できない` で違反になる。
同じ理由で `layer` / `kind` / `strength` のスカラもレコード直下として拾われず、
eval の keep-review 軸（C4 強度整合）の判定材料も欠ける。

**厄介な点**: **keep を選ばなければゲートは何も言わない。** designer が「keep にすると G2 で落ちる」と
気づいて全件 modify に倒せば、G2 は判定対象0件で静かに通る。前回 S1-2 と同じ
**vacuous pass の形**であり、今回 designer が親への報告で明示的に指摘しなければ気づけなかった。

**本 run での回避**: オーケストレータが `existing_customizations.md` の29レコードの見出しを
複数行形式（`- path: X` / 2スペース字下げの `layer:` `kind:` `strength:`）へ機械的に分割し、
design を巻き戻して designer に keep 判定だけを見直させた。結果 `.mcp.json` が keep になり
G8 のバイト同一照合が1件走った（`.claude/settings.json` は S1-2 の連鎖で keep にできず）。

**推奨する直し方（最小で確実な順）**:
1. **`parseSystemA()` の正規表現をパス部分だけに限定する**（`/^\s*-\s*path:\s*(\S+)\s*$/` にする、
   あるいは ` / ` 区切りの1行形式も受理して分解する）。後者なら既存の analyzer 出力がそのまま通る。
2. **`existing-customization-analyzer` の出力契約に「レコード見出しは `- path: <パス>` の1行に
   パスだけを書く」と明記する**（今は形式が自由なので analyzer が1行にまとめてしまう）。
3. **G2 に「keep が0件のとき、系統A のレコードが1件もパース出来ていないなら警告する」を足す。**
   「keep に値するものが無かった」と「keep を機構的に選べなかった」を区別できるようにする。
   前回の推奨③と同じ趣旨だが、今回の経路（パース失敗）でも発火するようにする。

## S1-2. G8 の `interface_change: none` 検査が frontmatter `name` にしか対応せず、宣言できない対象がある

**症状**: design-map が `modify` 26件すべてに `interface_change: none` を宣言したところ、
**うち11件は原本に frontmatter `name` が無く、G8 で「検査不能＝違反」になる**ことが判明した
（工程7完了後の G8 で11件ブロックされる予報。オーケストレータがスクリプトで数え直して裏取りした）。

該当11件: `CLAUDE.md`（frontmatter 無し）／`.claude/rules/*.md` 8件（6件は `paths:` のみで `name` 無し、
`research-discipline.md`・`tsod-workflow.md` は frontmatter 自体無し）／
`.claude/skills/impact-scope/scripts/scope-guard.mjs`／`.claude/README.md`。

**原因**: `gates/g8_non_regression.js`

```js
if (!originFm.present || !outFm.present || !('name' in originFm.frontmatter)) {
  violations.push(`${GATE}: modify "${r.path}" は interface_change: none を宣言しているが frontmatter name を持たない（検査不能＝違反…）`);
```

「対外インタフェースを変えない改修」という概念は frontmatter を持てない対象にも実在するのに、
**検証手段が frontmatter `name` の同一性しか無い**ため、宣言すること自体が違反になる。

**より悪い点（C3 との連鎖で両立できない）**: `gates/g2_keep_judgement.js` の C3 実照合は
「keep 対象の依存先が modify されるなら、その依存先が `interface_change: none` を宣言していること」を
要求する。`.claude/settings.json` の C3 は依存先 `scope-guard.mjs` の宣言に依存する。

- `scope-guard.mjs` に宣言を**残す** → G8 が「検査不能」で落ちる
- `scope-guard.mjs` の宣言を**外す** → `settings.json` の C3 が崩れて keep にできない

**どちらも選べない。** 本 run では後者を採り、`.claude/settings.json` は
「**内容変更を要求する要件は1件も無いのに keep にできない**」という判定になった。
結果、**keep なら走るはずの sha256 バイト同一照合が modify に落ちたことでむしろ走らなくなる**という
逆転が生じている（内容が変わらないファイルほど機械担保が弱くなる）。

**本 run での回避**: 11件から `interface_change: none` を外し、G8 の検査対象を
frontmatter `name` を持つ15件（SKILL.md 10・Subagent 5）に限定した。オーケストレータが
原本との `diff` と `sha256` で `.claude/settings.json`・`.mcp.json` の実質同一性を人手で確認した
（**意味判断でなく人手が機械担保の代替をしている**）。

**推奨する直し方**:
1. **種別ごとに「対外インタフェース」を定義し、それぞれに検査手段を用意する。** 例:
   - frontmatter を持つもの（SKILL.md・Subagent）→ 現行どおり `name`
   - rules（`paths:` のみ）→ `paths:` の値
   - `CLAUDE.md`・`.claude/README.md` → 見出し構造（`##` の列）
   - JSON（`settings.json`・`.mcp.json`）→ トップレベルキーの集合（`hooks` の配線点など）
   - 付随スクリプト（`*.mjs`）→ エクスポート／CLI 引数の形
2. 上記が重いなら、**最小の手当として「frontmatter を持たない対象への `interface_change: none` は
   検査不能ではなく『検査対象外』として扱い、違反にしない」**（宣言は残せるので C3 の連鎖が切れる）。
   ただし「宣言したのに検査されない」状態になるので、MANIFEST に検査されなかった旨を出すこと。
3. **C3 の実照合が G8 の検査可能性に依存していることを、どちらかのゲートのコメントに明記する。**
   今回この連鎖に気づけたのは designer が親へ報告したからで、ゲートの実装からは読み取れない。

## S2-2. `npm run recheck` がマーカー残存時に静かにスキップし、「違反なし」と報告する

**症状**: 工程4で spec.md の数え違い（§1 の強度内訳 deterministic 6件 ← 正しくは7件）を
オーケストレータが直したあと `npm run recheck -- 20260910_220906 spec` を実行したところ、

```
stage-guard: 通過 (spec:idempotent-cleanup)
[recheck] spec の再検査が完了した（違反なし）。
```

と表示された。**`spec.done` が残っていたため G1 は実際には走っていない**（冪等スキップ）。
`npm run reopen -- <ts> spec` でマーカーを削ってから recheck して初めて `spec:pass` になった。

**問題は出力の文面**: 「再検査が完了した（違反なし）」は、**検査していないのに検査結果のように読める**。
`idempotent-cleanup` の意味を知らないと、直した内容がゲートを通ったと誤解する。

**`/canon` skill には正しい手順が書いてある**（工程9→工程7の巻き戻し手順、P5 差し戻しの注記）。
しかし**recheck 自身の出力がそれと矛盾するメッセージを出している**のが危険である。

**推奨する直し方**:
1. `idempotent-cleanup` のときは「**検査していない**（`<stage>.done` が既に存在する）。
   成果物を直したのなら `npm run reopen -- <ts> <stage>` を先に実行せよ」と明示する。
   「違反なし」という文言を出さない。
2. 可能なら **recheck に「マーカーが存在するのに成果物の mtime がマーカーより新しい」検出を足し、
   その場合は警告する**（直したのに再検査していない状態を機械的に拾える）。

1. `spec-writer` の定義に「§9 が『なし』の場合、**箇条書きを使わず散文で書く**（G1 は

   ただし**判定を緩めると未決を隠せてしまう**ので、1 のほうが安全である。

## S3-3. write-scope-guard が Bash の複合コマンドを「宛先同定不能」で deny し、読み書き混在の一括処理ができない

**回避**: コマンドを1つずつに分解し、`.requests` の書込は Write ツールで行った。

**評価**: fail-closed の設計としては正しい。ただし**`.gate/` を `ls` するだけで
コマンド全体が落ちる**のは摩擦が大きい（`.gate/` の読取は禁止していないはずである）。

**推奨する直し方**: 「宛先同定不能」で落とす前に、**`&&`/`;`/`|` で分割して1つずつ判定する**
（分割後に同定できないものが1つでもあれば従来どおり deny）。前回 S3-7 の推奨と同じ方向。

## S3-4. Write ツールが sanctioned ツリー外を一律 deny するため、環境が指定する scratchpad が使えない

**症状**: 工程3で `project-profiler` の応答を `project_profile.md` の `## focused` 節へ
**逐語で永続化する**必要があったが（profiler は Write を持たない）、内容が大きく
Bash の heredoc がシェルのクォート処理で壊れたため、Write ツールで一時ファイルを作ろうとした。
環境が指定する scratchpad（`…/Temp/claude/…/scratchpad/`）へ書こうとして deny された。

```
sanctioned ツリー（output/<ts>/・work/<ts>/）外: ../../Users/…/scratchpad/focused.md
```

**回避**: `work/<ts>/_focused_fragment.md` に書いて `cat >>` で連結し、フラグメントを削除した。

**評価**: run in-flight 中に書込先を絞るのは正しい。ただし**環境（ハーネス）は
「一時ファイルは scratchpad を使え」と指示しており、ガードはそれを禁じている**。
両者が矛盾していることは記録しておく価値がある。

**推奨する直し方**: scratchpad（セッション固有の一時ディレクトリ）を sanctioned ツリーに加えるか、
`/canon` skill に「run 中は一時ファイルも `work/<ts>/` に置く（scratchpad は使えない）」と明記する。
**どちらでもよいが、今はどこにも書かれていない。**

## 運用上の観察（欠陥ではないが記録する）

### eval のラウンドを重ねると violation が一度増える

本 run の eval は3ラウンド回った。

| ラウンド | violation | 内訳 |
|---|---|---|
| round 1 | 8件 | correctness 3（description が旧スコープ）・context 5（SSoT 逐語重複） |
| round 2 | **12件** | correctness 3（R3 を現在形で記述）・security 5（担保文言の発火条件が主観的）・context 4 |
| round 3 | **0件** | — |

**round 1 の是正が round 2 の指摘を露出させた**（逐語重複を削った結果、その代替担保の妥当性が
新たな判定対象になった）。これは eval が機能している証拠であって異常ではない。
ただし「1周直せば clean になる」という期待は持たないほうがよい。

### ワーカーの件数申告は当てにならない（既知の再確認）

`requirements-recorder` は「deterministic 10件・advisory 16件」と報告したが実際は 7/19 だった
（ファイルの内容自体は正しい）。generator は3回目のパスで「実在確認済み（31パス）」と報告したが
実際は32件だった（`managed-paths.list` の全件実在は別途突合して確認）。
**報告の数値は転記前に必ず数え直す**（`.claude/rules/` の既存規律どおり）。

### `designer` の報告が欠陥の発見経路になっている

S1-1（parseSystemA）も S1-2（G8 の `name` 依存）も、**ゲートが検出したのではなく
designer が親への報告で明示したことで発覚した**。前回 S1-2 も同じ構図である。
**「ワーカーが親に報告しなければ気づけない欠陥」が繰り返し出ている**こと自体が、
ゲートの盲点の在り処を示している。

## 参考: 本 run で正しく機能したもの（退行させないこと）

- **G13 preflight**（`/canon` 展開時に自動発火）と**ランタイム・カナリア**。カナリアは
  `.gate/.canary` への Write が deny されることを実測し、配線の生存を確認した。
- **`npm run reopen`**。design を3回・generation を3回・spec を2回巻き戻したが、
  毎回ガードが再武装され、書き直し後に G1・G2・G7〜G12 が**実際に再実行**された
  （`spec:pass` / `design.done` の再鋳造で確認）。前回の申し送り「終端マーカーの巻き戻し」は
  解消されたままである。
- **承認の鋳造経路の一本化**。`.gate/**` への Write は最後まで deny され続け、
  承認はすべて `npm run approve` 経由で鋳造された。取消（`--revoke`）も正しく効いた。
- **`npm run eval:report`**。3ラウンドすべてで judge の出力契約違反と集約漏れを検出した。
  **この機械検証が無ければ「violation 0件」を3回とも誤読していた**（とくに round 1・round 3 の
  security 軸は violation 0 に見えて実は判定不能だった）。
- **`deploy/pre-deploy-check.js` → `deploy.js --confirm`**。uncaptured 0件を確認してから
  退避スワップで配置し、post-check の sha256 バイト同一確認まで通った。
- **`eval:bundle` の恒真バグ対策**。keep-review のバンドルに designer の `keep_conditions` 宣言と
  rationale が入らない設計は今回も守られており、judge は決定論的な材料だけで C2・C4 を判定した。
