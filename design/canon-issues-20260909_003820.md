## S1-1. `managed-paths.list` の形式が生成側と配置側で食い違い、配置が実際に失敗した

**症状**: `node deploy/deploy.js <output> <target> --confirm` が
`配置失敗のため配置前状態へ復帰した（rolled-back）: output に配置対象が無い: .claude/rules/**`
で失敗した（自動 restore は正しく働き、対象リポジトリは無傷だった）。

**原因**: `deploy/deploy.js` は `managed-paths.list` の各行を**具体的なファイルパス**として
`copyFileSync(src, dst)` に渡す。一方、design-map の「生成上の制約」と `readme-writer` の慣行は
**glob**（`CLAUDE.md` / `.claude/rules/**` / `.claude/skills/**` / …）で書く。両者が噛み合っていない。

**より悪い点**: `deploy/pre-deploy-check.js` は glob のままの list を**通してしまう**
（`消失予定: 0 件（retired 0 / uncaptured 0）` と報告）。したがって P8 の配置前照合では検出できず、
`--confirm` を打って初めて失敗する。

**潜在期間**: 前回 run（`design/canon-run-20260901_230930/output/.deploy/managed-paths.list`）も
glob で書かれている。この不整合は前回 run から潜在していた。

**G9 の vacuous pass**: `gates/g9_snapshot_completeness.js` は冒頭コメントで
「managed-paths.list ⇔ generated/（列挙パスが実際に生成されている）」を掲げているが、
glob 行に対してはこの照合が事実上素通りしている（`.claude/rules/**` というパスは実在しないのに
違反にならない）。`.claude/rules/gates-and-tests.md` の「ゲートの冒頭コメントが掲げる検査項目は
項目ごとに実装の有無を追跡する」に該当する。

**推奨する直し方（最小で確実な順）**:
1. **G9 に「`managed-paths.list` の各行が `generated/` 配下に実在するファイルであること」の検査を追加する。**
   これだけで生成段階で落ちるようになり、配置まで持ち越さない。故意に glob 行を入れた fixture で
   赤化することを確認すること。
2. `readme-writer`（および design-map の「生成上の制約」テンプレート）に「glob ではなく実ファイルを
   1行1件で列挙する」を明記する。
3. `deploy/pre-deploy-check.js` にも同じ検査を入れる（P8 で気づけるようにする）。

**本 run での回避**: 生成物を reopen して `managed-paths.list` を実ファイル28件の列挙に書き換え、
gen-guard を再実行して再配置した。

## S1-2. 既存改修モードで keep が構造的に0件になり、G8 の非回帰担保が丸ごと失われる

**症状**: designer が既存24レコードすべてを `modify` と判定し、keep が0件になった。帰結として
**G8 の sha256 バイト同一照合が本 run では1件も走らなかった**。既存改修モードにおける
「改修対象外のファイルが変わっていないこと」の機械担保が失われた。

**原因（規則適用の帰結であり designer の裁量ではない）**:
- **C1（正典適合）** の判定元は系統A の `canon_conformance`（`unknown_frontmatter_keys` 空・
  `deprecated_notation` 空・`frontmatter_keys_valid`・`tool_names_valid`）だが、
  `existing-customization-analyzer` はこれを構造化フィールドで出力しない。本 run の
  `existing_customizations.md` は散文の「レコード」形式で、`canon_conformance` の出現は grep 実測0件。
- **C5（プロジェクト実態整合）** の判定元は系統B の `ref_resolution` だが、系統A が
  `depends_on.project_refs` を出さないため照合対象が存在せず、`project-profiler` は
  「ref_resolution は未実施」と自己申告した。

「1つでも false なら keep 不可」の規則により、**既存改修モードでは keep が常に0件になる**。
これは今回のプロジェクト固有の事情ではなく、調査工程の出力形式に起因する構造的な問題である。

**代替担保（本 run で実際に採った手当）**: design-map に `change_class`
（`verbatim_regenerate` / `terminology_only` / `content_change`）を導入し、生成上の制約に
「原本を Read してから出力し、名指しした置換以外は1文字も変えない」を明記。eval の correctness 軸が
A2 非回帰名指し9ファイルを対象現物と実地 diff して裏取りした。**意味判断が機械担保の代替を
していることは記録しておくべき異常事態である。**

**推奨する直し方**:
1. `existing-customization-analyzer` の出力契約を構造化する（レコードごとに `canon_conformance`
   と `depends_on.project_refs` を必須フィールドにする）。
2. `project-profiler` の focused モードに `ref_resolution` 節を必須にする（系統A の
   `project_refs` を1件ずつ実在照合する）。
3. どちらも出せなかった場合に「keep 不可」で静かに全件 modify に倒れるのではなく、
   **調査工程の欠落として明示的に警告する**（eval の keep-review 軸は今回これを正しく報告したが、
   気づけるのは工程9＝設計が終わったあと）。

## S3-7. 読取専用の `node -e` が write-scope-guard に誤検知される

**症状**: 次のコマンドが `Bash 経由での保護パスへの書込を検出（保険的検査・シェル経路の封鎖・
広域スキャン（宛先同定不能））` で deny された。実体は **JSON の構文検査（読取のみ）**である。

```
node -e "JSON.parse(require('fs').readFileSync('output/.../settings.json','utf8'));console.log('OK')"
```

**原因**: `.claude/rules/gates-and-tests.md` が定める「保護パス判定は出現でなく宛先で行う」の例外として、
`node -e` は宛先を静的に確定できないため**出現ベースの広域スキャンへフォールバック**する。
その結果、`readFileSync` しかしていない `node -e` も、コマンド文字列に保護パス文字列が出現するだけで
落ちる。同様に `ls gates/ && node -e "...settings.json..."` も落ちた。

**影響**: 実害は小さい（`node --input-type=module -e` に書き換えて通った）が、
**保守作業のたびに書き方を試行錯誤する**コストが発生する。

**推奨する直し方**: `node -e` / `node --input-type=module -e` のスクリプト本文を軽くパースし、
書込 API（`writeFileSync` / `appendFileSync` / `rmSync` / `renameSync` / `mkdirSync` 等）が
出現しない場合は読取専用と見なして allow する。落とすのは「書込 API が出現する場合」に絞る。
`gates-and-tests.md` の「緩めた分は故意の違反注入で検出力が落ちていないことを示す」に従い、
`node -e` 経由の実書込が引き続き deny されることをテストで示すこと。
