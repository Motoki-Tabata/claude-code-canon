2. `generator` の定義に「builder へ渡す対象一覧は design-map から機械的に導出し、渡した件数と

## S2-5. keep-review judge が「バンドルしか読まない」契約ゆえに、事実と異なる violation を出す

**症状**: round 1 で keep-review judge が `.mcp.json` に C2 violation を出し、その根拠として
「利用有無の観測強化等の緩和措置も伴わない」と述べた。しかし生成物

実在しており、**根拠が事実に反していた**。

**原因**: 恒真バグ防止のため（§16.3）、keep-review judge には designer の `keep_conditions` と
rationale を渡さない。その結果 judge は「緩和措置が他ファイルに存在するか」を確かめる材料を持たず、

**本 run での回避**: オーケストレータが round 2 で当該事実（ファイル名・行番号）を注入し、
judge は violation を撤回した。

**推奨**:
1. designer の主張（`keep_conditions`・rationale）は引き続き withhold したまま、
   **keep 対象を参照している生成物の該当箇所**をバンドルに含める（「誰がこのファイルを SSoT として

2. 少なくとも `quality-checklist` に「不在を根拠にする前に、生成物全体を grep して確かめる」旨を書く。
   judge は `Grep`/`Glob` を持っている（`tools: Read Grep Glob Write`）ので実行可能である。
3. 本件は、**judge の verdict の根拠が事実か**をオーケストレータが検算する必要があることも示している。
   `/canon` skill 工程9 に「violation の根拠に『存在しない』が含まれる場合は横断 grep で裏取りする」を加える。

## S3-5. `design/` は sanctioned ツリー外のため、run 中は canon 改修案そのものを書けない

**症状**: 本ファイル（`design/canon-issues-<ts>.md`）は run の知見を記録する場所だが、
`write-scope-guard.js` は sanctioned ツリー（`output/<ts>/`・`work/<ts>/`）外への書込を一律 deny する
（同ファイル102行）。run in-flight 中は本ファイルを書けない。

**実際には書けた理由**: `TERMINAL_STAGE = 'generation'`（`gates/lib/run.js:44`）であり、
`generation.done` が鋳造済みだと `currentRunTs()` が null を返してガードが素通りになる
（同 249〜259行）。工程10（配置）は終端マーカーより後なので、配置後は書ける。

**注意**: この挙動により、**`work/.session-ts` の残置は「ガードが武装したまま」を意味しない**。
`reopen` の警告文（`tools/reopen.js:155`）は「放置すると `.session-ts` の残置と同じ事故になる」と述べるが、
終端マーカー鋳造済みの run については保守編集は deny されない。警告文がこの区別を書いていないため、
オーケストレータが「ガードが残っている」と誤認しうる（今回実際に誤認しかけた）。

**推奨**:
1. `tools/reopen.js` の警告文に「終端マーカー（`generation.done`）が鋳造済みなら `.session-ts` が
   残っていてもガードは素通りする。危険なのは終端マーカー未鋳造のまま放置する場合である」を加える。
2. `/canon` skill に「run の終い方」を1節置く（`.session-ts` は削除しなくてよい・`session-init.js` が
   情報ログを出すだけで害は無い、という現状の設計を明文化する）。`tools/` に完走コマンドが無いため、
   オーケストレータが毎回この判断を自前で行っている。

## S3-6. 配置成功後、案内された `.bak` が実地に存在しなかった（原因未特定）

**症状**: `--confirm` が `status: deployed` で終わり、終了メッセージは
「2) `<target>/.claude-canon.bak.20260922_172924` から手動 restore（`.bak` の掃除は人間が明示的に行う）」
と案内した。しかし配置の翌作業でこのディレクトリを探したところ、**サンドボックス内・サンドボックス外の
どちらから見ても存在しなかった**（`ls -a | grep bak`・`find -maxdepth 1 -name '.claude-canon.bak*'` とも空）。

**原因は特定できていない**。本 run ではその前に、EBUSY による部分配置からの復旧として
`.bak` を（`cp -a` で対象へ戻したうえで）人手で削除している。成功した2回目の `--confirm` が
`.bak` を作らなかったのか、作ったものを後段の作業が消したのかを、セッションの記録からは確定できなかった。
**断定を避けてここに観測事実だけを残す。**

**気に留めるべき点**: `deploy()` の step1 は `walkManaged(targetDir)` が返した分だけを `moveFile` し、
`bakDir` の作成は `moveFile` → `ensureParent` の副作用でしか起きない（`deploy/deploy.js` 103〜107行）。
したがって **`walkManaged` が0件を返す状況では `.bak` は作られないのに、成功メッセージは
`.bak` からの restore を案内する**。この分岐は今回の症状と整合する経路の1つであり、
少なくとも「案内した復旧手段が実在するか」を確かめずに出力している点は確かである。

**推奨**:
1. 終了メッセージを出す前に `existsSync(bakDir)` を確認し、無ければ
   「退避対象が0件だったため `.bak` は作成していない。ロールバックは対象側 git の revert のみ」と出す。
2. `status: deployed` の戻り値に `baked: retiredManaged.length` を含め、RUN.md の手順と突き合わせられるようにする。
3. 回帰テスト: 管理ファイルが1つも無い対象へ配置し、`.bak` 不在と整合する終了メッセージが出ることを確かめる。

## 参考: 本 run で spec 側に手作業で足した仕組み（canon 本体の機能候補）

- **必達項目を designer の優先順位判断の対象外にする節**。本 run では対象側 lessons の3件
  （ゲート⑥後のセッション切替・以降の不具合のワーカー委譲・効果測定の文脈成長）が
  「反映されない」リスクがあったため、spec に **A1-8**（3件の反映先ファイルと挿入位置を名指しし、
  designer の優先順位判断の対象外と宣言する節）を人間ゲート P4 の差し戻しで追加した。
  同種の「これは必ず入れる」は既存改修モードで毎回発生するので、`spec-writer` の
  テンプレートに **mandatory 節**として構造化する余地がある（G1 で「mandatory の各項目が
  design-map の record に対応しているか」を機械照合できる）。
- **数値目標ではなく質で見る受け入れ基準**。当初 spec A1-4 は「常時ロード L1 が 242行を超えない」
  だったが、教訓の反映は必然的に L1 を増やすため A1-1／A1-8 と衝突する。P4 で
  「同一内容が2箇所以上に無いこと（`paths:` 差による意図的二重管理は除く）」＋「242行は参照値であり
  合否条件ではない」へ書き換えた。`spec-writer` に「行数・件数を合否条件に使わない」制約を置くとよい。
