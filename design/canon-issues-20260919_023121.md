## S1-1. `deploy.js` が退避（step1）の途中で例外を投げると restore を通らず、対象を半壊状態で残す

**症状**: `node deploy/deploy.js <output> <target> --confirm` が `.mcp.json` の rename で
`EBUSY` を投げて異常終了した。**その時点で `.claude/**` の管理ファイル29件が
`.claude-canon.bak.20260919_023121/` へ移動済み**で、対象リポジトリから消えた状態のまま放置された。
自動 restore は走らず、終了メッセージにも「退避済みで対象が欠けている」旨は出ない（Node のスタックトレースのみ）。

**原因**: `deploy/deploy.js` の `deploy()`。step1（`walkManaged()` → `moveFile()` の退避ループ）が
`try { … } catch { restore(…) }` の**外**にある。`try` が包んでいるのは step2（配置）と step3（post-check）だけ。
`moveFile()` は `EXDEV` 以外の例外をそのまま再送出する。

**EBUSY の発生源**: Claude Code の Bash サンドボックス（bubblewrap）が対象の `.mcp.json` を
読み取り専用でバインドマウントしていた（`mount` に `/home/…/vehicle-intake-management/.mcp.json type ext4 (ro,…)`）。
バインドマウントの対象は rename できないため `EBUSY` になる。サンドボックス有効環境で `--confirm` を
サンドボックス内から実行すると**毎回**再現する見込み（`.mcp.json` は canon の管理パス）。

**本 run での回避**: オーケストレータが `.bak` 内の29件を元の位置へ `mv` で戻し、`git status` がクリーンに
戻ったことを確かめ、空の `.bak` を削除した。そのうえで `dangerouslyDisableSandbox` で `--confirm` を再実行し
成功（post-check 通過・32件 sha256 同一）。

**推奨**:
1. step1 を `try` の内側へ入れ、途中失敗時は「移動済みの分だけ」を戻す（`restore()` に移動済み一覧を渡す）。
2. 退避の前に、管理パス集合の各ファイルが rename 可能か（親ディレクトリ書込可・マウントポイントでない）を
   事前検査し、不可なら何も動かさずに拒否する。
3. 失敗時の終了メッセージに「対象の状態（無傷／restore 済み／半壊）」を必ず出す。
4. `/canon` skill 工程10 と `RUN.md` に「サンドボックス有効環境では `--confirm` はサンドボックス外で実行する」を明記する。
5. 回帰テスト: 退避ループの途中で `renameSync` が `EBUSY` を投げる状況を注入し、対象が配置前と同一に戻ることを検証する。

## S1-2. agent-builder の書き出し残骸 `</content>` が6 agent の最終行に混入し、ゲートも eval も検出しなかった

**症状**: 配置後の差分レビュー（対象側 PR 作成前）で、`.claude/agents/*/*.md` の6件すべての最終行に
`</content>` という1行が付いているのを発見した。P5 差し戻し後の再生成（agent-builder・round 2）の生成物で、
**決定論ゲート G3〜G12・eval 5軸（canon・context を含む）・配置の post-check のいずれも通過していた**。
post-check は output とのバイト同一を見るだけなので、output 自体が壊れていれば素通りする。

**影響**: Subagent 定義の本文末尾に意味の無いタグが残る（frontmatter は無傷のため起動は壊れない）。
生成物の本文を機械的に検査する層が無いことの実例であり、同種の残骸（`</parameter>` 等）が
frontmatter 側に混入すれば起動不能になりうる。

**本 run での回避**: 対象リポジトリと `output/20260919_023121/generated/` の両方から、最終行が
`</content>` そのものである場合に限りその1行を削除し、32件のバイト同一を再確認した（PR #33 本文に明記）。

**推奨**:
1. G12（出力ファイル単位のスキーマ適合）に「ツール呼び出しの書式片（`</content>`・`</parameter>`・
   `<parameter name=` 等）が行単位で現れたら違反」の検査を加える。コードフェンス内は除外。
2. 回帰テスト: 本文末尾・frontmatter 直後・コードフェンス内の3位置に残骸を注入し、前2者だけが違反になることを確かめる。
3. agent-builder 等の builder 定義に「Write の content に書式タグを含めない」注意を置くのは補助に留め、担保は 1 で行う。

## S2-1. investigator 配下（系統A・系統B）の報告が investigator ではなくメインへ配送される

**症状**: investigator が系統A・系統B を spawn した直後に turn を終えた（既知の failure mode）。その後、
両ワーカーの `SubagentHandback` は **investigator ではなくメイン（オーケストレータ）へ**届き、
investigator は結果を受け取れなかった。investigator 自身は「この環境では Agent 呼び出しが常にバックグラウンド実行
となり `run_in_background: false` が提供されない」と報告している。

**本 run での回避**: オーケストレータが各ワーカーのトランスクリプト（JSONL）から `SubagentHandback` の
`message` を逐語抽出して `work/<ts>/.fragment-{A,B}.md` に置き、`SendMessage` で investigator を再開させて
永続化させた。

**副次**: investigator の転記は系統A はバイト同一だったが、系統B は1箇所（Gradle プラグインの列挙順）が並べ替わった
（逐語契約違反。内容は同じ）。

**推奨**:
1. `/canon` skill 工程1と `investigator` 定義に「配下の報告が親に届かない環境」を前提とした手順を書く
   （例: 系統A・B の起動をオーケストレータが直接行い、investigator は永続化専任にする。あるいは深さ2を諦める）。
2. 逐語転記の検証として、永続化後に「ワーカー報告と成果物の diff が空」をオーケストレータが確かめる手順を置く。

## S3-4. 配置後の push で、canon セッションには対象側の sandbox 例外が効かない

**症状**: 配置後に canon のセッションから対象リポジトリで `git push` すると、pre-push の gitleaks が
`permission denied while trying to connect to the docker API` → 「シークレットらしき文字列を検出しました」
（検査未実行の誤表示）で失敗した。対象側 `.claude/settings.json` の `allowAllUnixSockets: true` は
対象リポジトリで起動したセッションにしか効かず、canon リポジトリで起動したセッションには効かない。

**本 run での回避**: `dangerouslyDisableSandbox` で push を再実行し、gitleaks は `no leaks found` で通過した。

**推奨**: `/canon` skill 工程10（または RUN.md）に「配置後のコミット・push は対象リポジトリで起動したセッションで行う。
canon のセッションから行う場合は対象側の sandbox 例外が効かない」と明記する。
