# findings.md（要件の主張の確認）

ヒアリングで出た要件の主張を、対象の実物で確かめた結果を書く。**渡された主張に関係する箇所だけ**を読み、無関係な事項を書き足さない（調査が広がると、下流の文書が際限なく大きくなる）。主張は、ユーザーの言葉や対象の lessons・README の文言から来ているので、実物と食い違うことがある。食い違いを見つけるのがこの調査の目的である。

入力として、主張の一覧（要件の仮の ID・主張・確かめたいこと）と、対象の worktree のパスが渡される。

## テンプレート

```markdown
## findings
- topic: <論点>
  req: <要件の仮の ID（R1…）>
  confidence: 実物で確認|文言のみ
  evidence_paths: [src/a.ts:12-40, src/b.ts]
  summary: <実物が示すこと。主張と食い違うときは、どう食い違うか>
unverified:
  - topic: <実物では確かめられなかった論点（Claude Code の仕様に依存するもの、実行しないと分からないもの）>
    req: <R1>
    reason: <なぜ確かめられなかったか>
extractable_templates:
  - source: <抜き出せる素材のパス>
    as: <Skill の supporting file などとしてどう使えるか>
    note: <補足>
```

## 確度の付け方

- **実物で確認**: 対象のファイルを読んで、主張が成り立つ（または成り立たない）ことを確かめた。
- **文言のみ**: 実物で確かめられず、文言（lessons・README・コメント）の記述しか根拠が無い。`unverified` にも載せる。
- 「公式で確認」は investigator には付けない。WebFetch を持たないので、Claude Code の仕様に依存する主張は `unverified` に載せ、メインが公式のドキュメントで確かめる。

## 調べ方

- 語がどこにどれだけあるかは、Grep の `output_mode` を `count` か `files_with_matches` にして取る。該当行の抜き出し（`content`）は、分布を見て対象のファイルを絞ってから行う。ディレクトリ全体を `content` で引くと出力が大きくなり、会話に入らずにファイルへ退避される。
- 多数の語を `|` で並べた検索は、語ごとの分布を見てから必要な語に絞る。
- 参照元（別プロジェクトの一式）が渡されたときは、渡された `path` の配下も、主張に関係する範囲だけ読む。参照元は移植の基準であり、`topic` に「参照元」と明記して区別する。参照元の中身を対象の事実として書かない。

## 書き方

- `evidence_paths` は必須。根拠のパスを示せない論点は書かない（`unverified` に載せる）。`extractable_templates` は、差分を対象に接地させる素材になる。
- 食い違いを丸めない。主張が実物と違うときは、`summary` の先頭に「食い違い:」と書き、主張と実物を1文ずつ並べる。

## 値の語彙

1. `evidence_paths` は対象ルート相対のパスを裸で書く。バッククォートで囲まない。絶対パスも書かない（worktree の外を指してしまう）。
2. 複数のパスは `[a, b, c]` の角括弧が必須。
3. 末尾に行番号 `:N` や行範囲 `:N-M` を付けてよい。1項目の中にカンマ区切りの複数行番号（`path:12,40`）は書かない。複数行を示すなら行範囲にするか、論点を分ける。
4. `evidence_paths` は同じ行に書く。次行以降に箇条書きで並べない。

## 書いたあとの確認

自分の出力を Read し直し、渡された主張の全件が `findings` か `unverified` のどちらかにあることを確かめる。
