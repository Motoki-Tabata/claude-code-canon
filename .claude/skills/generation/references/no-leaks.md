# 生成物に書いてはいけないもの

生成物は、配置されたあと**対象プロジェクトの人と Claude が読む**。claude-canon の作業の文脈（どの要件から、どの run で、どう作ったか）は、読み手の側には存在しない。存在しないものを指す文は、読み手が辿れない参照になり、意味のない行になる。

## 書かないもの

1. **読み手が解決できない参照**
   - 生成元の要件 ID（`R6`・`A1-2` など）、spec・design-map・run の節や番号、run 外の事故の番号。対象のリポジトリには、それらが無い。
   - 定義の無い規約の名前（「Skills 共通規約」など、どこにも書かれていないものを指す表現）。規約を指すなら、その規約を同じ生成物の中に書くか、書かれた場所のパスを示す。
   - 理由の代わりに ID を置くこと（「R6 のため」）。理由は、読み手に分かる言葉で書く。
2. **作者向けの編集メモ**
   - frontmatter や本文に、生成の指示の名残（「`disable-model-invocation` は付けない」「この行は builder が…」）を残さない。
   - ツール呼び出しの閉じタグなど、生成の過程で紛れた断片（verify の V5 が止める）。
3. **差分・経緯を示す表現**
   - 「移設した節」「旧〜は廃止」「以前は〜だった」「〜から統合した」のように、別の版との比較でしか意味が通らない文。生成物は、その時点の全量の姿だけを書く。廃止や統合の経緯は、MANIFEST が記録する。
4. **検証していない実績の主張**（「テスト済み」「動作確認済み」）。

## 書くもの

- なぜそうするのか（why）。ルールには理由を添える。理由が読み手の現場で通じる言葉で書かれていれば、場面が変わっても判断を誤らない。
- 対象プロジェクトに実在するパス・コマンド。実在を確かめたものだけ。focused.md の `extractable_templates` と `evidence_paths` が、接地の材料になる。

## 書き終えたときの自己点検

自分の出力に対して、次を探す。見つかれば直す。

- `R[0-9]`・`A[1-4]-`・`spec`・`design-map`・`run`・`builder`・`slice` の語。
- 「〜こと」の文が、参照先を持たない「共通規約」「上記のルール」を指していないか。
- frontmatter に、キーの値でない説明文（編集メモ）が入っていないか。
