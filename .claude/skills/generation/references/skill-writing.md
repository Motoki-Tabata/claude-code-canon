# Skill の書き方（skill-creator の執筆指針の要約）

出典: anthropics/skills の skill-creator。正典 `docs/L2_SKILLS.md` と衝突したら正典に従う。ここでは、良い Skill に共通する書き方だけを抜き出す。

## description が、発動の判定のすべて

- description は、Claude が Skill を使うかどうかを決める**ほぼ唯一の手がかり**。「何をするか」と「どんな場面で使うか」の両方を書く。「いつ使うか」は本文でなく description に書く（本文は発動してからしか読まれない）。
- 具体的に書く。「データを扱う」でなく、どのファイル・どの依頼・どのキーワードのときか。ユーザーが Skill の名前を言わなくても当てはまる場面を含める。
- Claude は Skill を**使い損ねる**傾向がある。使うべき場面を、少し積極的に列挙する（「〜のときは、〜と明示されていなくても使う」）。

## 構造と段階的開示

- 3段で読み込まれる: (1) name と description は常に文脈にある (2) SKILL.md の本文は発動したときに読まれる (3) references・scripts・assets は必要になったときだけ読まれる。
- **SKILL.md は500行未満**。近づいたら、references に分け、SKILL.md には「いつ・どれを読むか」の道しるべを書く。300行を超える reference には、冒頭に目次を置く。
- 複数の領域・variant を扱うなら、variant ごとに reference を分け、SKILL.md は選び方だけを持つ（読まれるのは該当する1つだけになる）。
- 決定論で済む反復作業（整形・検証・変換）は `scripts/` に置く。スクリプトは文脈に読み込まずに実行できる。

## 書き方

- **why を書く**。「必ず〜せよ」の大文字の連呼より、なぜそれが大事かを説明する。理由が分かれば、想定外の場面でも判断を誤りにくい。
- 命令形で書く。特定の例にだけ効く狭い指示でなく、一般化できる指示にする。
- 出力の形が決まっているなら、テンプレートを**そのまま**示す（「この構造を使う」として見出しまで書く）。例は、入力と出力の対で示す。
- 驚きを与えない。Skill の中身は、description から想像できる意図に沿っていること。

## 仕上げ

書いたら、新しい目で読み直して削る。読まれない説明・自明な注意書き・重複を消す。試すなら、利用者が実際に言いそうな依頼を2〜3個作って、発動と結果を確かめる（description の発動精度の最適化は、Skill の eval を並列に回せるオーケストレーターが任意で行う。builder は行わない）。
