# 構成と責務

使う機能が決まったら、各カスタマイズの1文責任と、書込スコープ、検証の主体を決める。機能をどう組み合わせるか（委譲・並列・強制・配布）は次の段階（[orchestration-patterns.md](orchestration-patterns.md)）で決める。

## 責務の書き方

各カスタマイズに**1文で言える責任**を割り当てる。1文で言えなければ、責務が2つ混ざっているので分ける。design-map の `## 構成と責務` に、機能の節ごと・カスタマイズごとの1文責任を書く。機能のどれに置くかの根拠は `canon-reference/references/selection.md` §1・§3 にある。

## Write Scopes（役割にファイル所有権を割り当てる設計では必須）

サブエージェントが複数いて、それぞれが担当のディレクトリを持つ構成では、`## Write Scopes` を書く。次の4点を満たす。

1. **役割ごとの常設の書込範囲**（許可する glob の一覧）。
2. **ビルド設定・構成ファイル（依存の追加・実行時設定）の扱い**。常設の範囲に含めるか、宣言駆動の例外（spec や要件文書に明記されたときだけ、役割を問わず許可）にするかを、必ずどちらかに決めて書く。書かないと、常設にも例外にも書かれないファイルが、サブエージェントの「範囲外なら停止する」という自己チェックが発火しない死角になる。常設の表に混ぜて恒常化すると、要件が想定していない依存の追加まで常に許されてしまう。選ばなかった側の理由も書く。
3. **強度**: `canon-reference/references/selection.md` §4 の段階のどれで担保するか。Hook は呼び出したサブエージェントを識別できないので、役割別の書込範囲は advisory にしかならない。
4. **代替の担保**: advisory にとどまるなら、サブエージェントの本文に自己チェック手順を書き、事後にレビューする、という担保を明記する。宣言だけで担保が済んだことにしない。

役割分担が無い設計（サブエージェントが1体、Skill だけ、など）は、`## Write Scopes` に「N/A（役割分担なし）」と書く。

## 検証の主体

生成物に含まれるテストの実行やスクリプトの動作確認のように、コマンドの実行を要する検証は、主体を「オーケストレーター」と書く。ワーカーは実行できない。
