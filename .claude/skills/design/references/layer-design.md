# 層数と責務

使う機能が決まったら、オーケストレーションの層数（2層・3層）と、各カスタマイズの1文責任を決める。「2層」「3層」は claude-canon 独自の整理用語で、公式の用語ではない。

## 層数の選び方

```
単発か、繰り返しか？      単発 → 単層（inline）／繰り返し → 次へ
ワークフローか、役割か？  ワークフロー → L2 Skill（2層）／役割 → L3 Subagent（2層）
Subagent の中で多段処理が要るか？  要らない → 2層で確定／要る → 次へ
何を呼ぶか？  Skill → 3層 パターン D／MCP → 3層 パターン E／Hook → 3層 パターン F／
              別の Subagent → 可（既定3階層）。既定を超える・独立プロセスなら Agent Teams か /batch
```

| 要件 | 推奨 |
|---|---|
| 単発の短い作業 | 単層（inline） |
| 専門レビューを1回 | 2層 パターン A |
| 長い探索 | 2層 パターン B（`context: fork`） |
| 専門の役割を継続して使う | 2層 パターン C |
| 多段の専門処理 | 3層 パターン D（Subagent と Skill） |
| 外部サービス連携 | 3層 パターン E（Subagent と MCP） |
| 監査・遮断 | 3層 パターン F（Subagent と Hook） |
| 大規模で複雑なオーケストレーション | Dynamic Workflows（自動生成の対象外。手動対応の項目として明記する） |

## 公式の制約（設計が破ってはならない）

- Subagent の nesting は既定3階層。深度の上限に達すると Agent ツールが外れて打ち止めになる（`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` で調整できる）。多段の委譲が要らない Subagent には、spawn の指示を書かない。
- fork は別の fork を spawn できない。Agent Teams の teammate は teammate を spawn できない。
- `disable-model-invocation: true` の Skill は、`skills:` で preload できない。
- `context: fork` には、実行すべき具体的なタスクが要る（指針だけの Skill を fork すると、Subagent は何もせず終わる）。

## 責務の書き方

各カスタマイズに**1文で言える責任**を割り当てる。1文で言えなければ、責務が2つ混ざっているので分ける。design-map の `## レイヤー構成` に、カスタマイズごとの1文責任を書く。

## Write Scopes（役割にファイル所有権を割り当てる設計では必須）

L3 の Subagent が複数いて、それぞれが担当のディレクトリを持つ構成では、`## Write Scopes` を書く。次の4点を満たす。

1. **役割ごとの常設の書込範囲**（許可する glob の一覧）。
2. **ビルド設定・構成ファイル（依存の追加・実行時設定）の扱い**。常設の範囲に含めるか、宣言駆動の例外（spec や要件文書に明記されたときだけ、役割を問わず許可）にするかを、必ずどちらかに決めて書く。書かないと、常設にも例外にも書かれないファイルが、Subagent の「範囲外なら停止する」という自己チェックが発火しない死角になる。常設の表に混ぜて恒常化すると、要件が想定していない依存の追加まで常に許されてしまう。選ばなかった側の理由も書く。
3. **強度**: 上の4段階のどれで担保するか。Hook は呼び出した Subagent を識別できないので、役割別の書込範囲は advisory にしかならない。
4. **代替の担保**: advisory にとどまるなら、Subagent の本文に自己チェック手順を書き、事後にレビューする、という担保を明記する。宣言だけで担保が済んだことにしない。

役割分担が無い設計（Subagent が1体、L2 だけ、など）は、`## Write Scopes` に「N/A（役割分担なし）」と書く。

## 検証の主体

生成物に含まれるテストの実行やスクリプトの動作確認のように、コマンドの実行を要する検証は、主体を「オーケストレーター」と書く。ワーカーは実行できない。
