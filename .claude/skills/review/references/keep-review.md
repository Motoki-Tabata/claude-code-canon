# keep-reviewer の判定

## なぜあなたが要るのか

keep は「変えない」判断なので、差分に出ず、人間のレビューでも最も気づかれにくい。verify の V7 は、K1・K3・K5 を事実として照合し、K2・K4 については「designer が true と宣言したか」の形式しか見られない。あなたがいなければ、designer が `K2: true` と書きさえすれば、誰も中身を確かめないまま keep が通る。あなたは、V7（形式）→ keep-reviewer（意味）→ P3・P4（人間）の、中段である。

## 入力

`work/<ts>/review-bundle/keep-review/<case>.md`（ケースごとに1ファイル）。review-bundle が決定論で作ったもので、対象の実体・existing.md の事実・spec の新要件と統合方針・requirements（確定要件・constraints・conflicts）を含む。

- **designer の `keep_conditions` の宣言と rationale は、意図的に含まれていない**。判定対象自身の主張に引きずられて、常に問題なしと答える恒真を避けるためである。設計者が「問題ない」と考えた事実は、判定の材料ではない。もしバンドルにそれらが混入していたら、根拠に使わず、混入を報告する。
- バンドルの「生成物内での言及（逆引き）」の節は、対象を名指ししている生成物の箇所を `file:line` で一覧したもの。

## 判定する3つ

- **K2 要件非抵触**: 既存を変えずに維持したとき、新要件・統合方針と、**責務が重複**または**方針が競合**しないか。
  - 重複: 新しく作る生成物と役割が被る（同じ責務の置き場が2つになる）。
  - 競合: 新要件の方針と食い違う（統合方針が一本化を求めているのに、二重化が残る）。
  - **領域が近いだけでは違反にしない**。責務が実際に重なるかで判断する。統合方針が明示的に役割を分けているなら、重複ではない。
- **K4 強度整合**: 既存が担う強度（advisory・deterministic・enforced）が、要件の `strength_needed` と constraints に矛盾しないか。「手順書（advisory）で、deterministic の要件を担う」は矛盾。ただし、統合方針が既存を補助的な役割に位置づけているなら、強度の差だけでは矛盾にならない。
- **merge の統合先（merge_target）**: 統合先の**実体（生成物の本文）が、統合元の中核の責務を実際に内包しているか**を、バンドルの「統合先の実体」で確かめる。トピックやライフサイクルが近いだけ、要件が統合を名指ししているだけでは、吸収ではない。統合先が統合元の中核の手順や内容を落としている（部分的にしか取り込んでいない）なら違反にする。「生成の完成度は別の観点」として見送らない（見送ると、統合で内容が半分落ちても、吸収を見る検査が他に無いので、誰も気づかないまま配置される）。責務が重ならない先に寄せるのも、当然に不当である。

## 手順

1. バンドルを1件ずつ読む。判定の材料はバンドルと `output/<ts>/`（生成物）だけである。対象プロジェクトの実体は渡されないので、バンドルに無い事実は推測で補わず、確信度を下げた指摘で表す。
2. 判定するときは、「生成物のどこにも言及が無い」と書く前に、バンドルの逆引きの節と Grep で確かめる（[SKILL.md](../SKILL.md)「不在を根拠にする前に確かめる」）。
3. 回付された**全ケース**を判定する。問題なしでも、判定した証跡として1件書く（[output-contract.md](output-contract.md)）。未判定は「問題なし」でなく、カバレッジの失敗として扱われる。
4. **迷いは clean でなく、確信度を下げた違反で表す**。低い確信度の指摘は、P4 で人間が確認して終わる。

## 判定しないこと

K1・K3・K5・frontmatter・ツール名・sha256（verify が判定済み）。

## 修正後の再判定

全ケースを判定し直さない。プロンプトで渡された、前回に違反だった対象と、変更のあった keep・merge の対象のバンドルだけを読む。前回の違反が解消したかは、最新のバンドル（逆引きを含む）で確かめる。
