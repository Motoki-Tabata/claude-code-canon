# reviewer の4観点

入力（プロンプトで渡される）: `output/<ts>/generated/`・`output/<ts>/spec.md`・`work/<ts>/slices/`（design-map の切り出し）・`work/<ts>/investigation/`・対象プロジェクトのルート（実態への接地の確認に使う）・`work/<ts>/requirements.md` の constraints。**design-map.md の全文は先に読まない**（大きい）。設計意図は slices で確かめ、スライスに無い節が要るときだけ design-map.md の該当の節を読む。

## 1. correctness（要件を満たすか・実態に接地しているか）

- **A1 functional**: spec §8 の `functional` の受入基準を、生成物が実際に満たすか。「それらしい文書がある」でなく、「その基準が達成される」かで見る。
- **接地**: 実在しないコマンド・スクリプト・パスを、手順として書いていないか。Read・Grep・Glob で対象プロジェクトを確認してよい。README の記述を鵜呑みにして、実在しない手順を書く事故が起きうる領域である。
- **要件との対応**: spec の各新要件に対応する生成物が実在し、責務が要件を覆っているか。
- **実行コードのロジック**: 生成物に実行されるコード（Hook のスクリプト・MCP の `command` と引数）があれば、意図した発火条件で動き、ブロックすべき場面で正しい終了コード（Hook の exit 2 など）を返すかを読んで確かめる。読んだだけで「動く」と断定せず、実行して確かめていないことを書き添える。

## 2. security（権限設計と安全性）

- **最小権限の実質**: 各 Subagent の `tools` が、役割に対して過剰でないか。読むだけの役割に Write・Edit を与えていないか。
  - 粒度の注意: Subagent の `tools` は**ツール種別の列挙**で、`Bash(npm test:*)` のようなコマンド単位の権限指定子は持てない（それは settings.json の `permissions` の領分）。Bash を実際に要する役割には、素の `Bash` が最小の表現可能な付与である。「コマンドを絞れていない」を理由に違反としない。過剰かどうかは、「そのツール種別自体が、その役割に不要か」で見る（例: 指摘するだけの役割に Write・Edit・Bash）。
- **実行コードと権限設定の安全性**: Hook のスクリプトや MCP の `command` が、未検証の入力（ツール入力の JSON・ファイルパス・環境変数）をクォートせずにシェルへ渡していないか。`settings.json` の `permissions.allow` が、要件に対して広すぎるパターン（`Bash(*)` に近いもの）になっていないか。
- **危険な操作の誘導**: 生成物の手順が、確認なしの破壊的な操作・広範な削除・認証情報の平文の取り扱いを促していないか。
- **権限と要件の釣り合い**: 要件が求める強度に対して、過剰な権限で解いていないか。
- **organization_policy**: requirements.md の `constraints.organization_policy`（自由文）があれば、生成物の手順がそれに反していないか。verify の V9 はこれを機械で判定できないと明示して見送っているので、意味を読んで判定できるのはあなただけである。無ければ、この観点は該当なしと書く。

## 3. 正典の意図（スキーマでなく趣旨への適合）

- **段階的開示**（`docs/L2_SKILLS.md`）: SKILL.md が入口として機能し、詳細を必要なときに開く構成になっているか。すべてを1ファイルに詰め込んでいないか。
- **description の委譲トリガーの質**（`docs/L3_AGENTS.md`）: いつ委譲・発動すべきかが具体的に書かれ、他の役割と区別できるか。抽象的すぎて発火しない、または広すぎて誤発火する記述になっていないか。
- **層の当てはまり**（`docs/00_INDEX.md` §4）: その責務を、その層に置く理由が成り立つか。L1 に手順を詰め込む、L3 に静的な知識を置く、といった取り違えが無いか。
- 指摘には、正典の出典（ファイル名と節）を添える。

## 4. context（コンテキストの効率）

正典 `docs/BEST_PRACTICES.md` §1.1「コンテキストは最も貴重な資源」に基づく。

- **重複**: 同じ内容が複数のファイルに書かれ、更新のときに片方が腐る構造になっていないか。
- **読まれない冗長**: 判断に使われない説明・自明な注意書きで、実効的な指示が埋もれていないか。
- **責務の肥大**: design-map が与えた1文の責任に対して、実体が別の責務まで抱えていないか。
- **preload の妥当性**: 常に読み込む Skill が、本当に常時要るか（毎回のコストになる）。
- **量の目安**: verify は行数を検査しない。CLAUDE.md の200行（`docs/L1_CONTEXT_MANAGEMENT.md`）や SKILL.md の500行（`docs/L2_SKILLS.md`）を超えていないかは、ここで見る。超えていれば、何を Rules・Skill・references へ分けるべきかを具体的に示す。
- 指摘は、「どのファイルの何が、重複か冗長か」を具体的に示す。抽象的な「冗長です」は、行動に移せない。

## 修正後の再レビュー

修正ループの2周目以降は、全体を判定し直さない。プロンプトで渡された、変更のあった対象と、前回に指摘した対象だけを見る。前回の指摘が解消したかは、変更後の実体で確かめる（指摘に合わせて結論だけを変えない）。security は、変更があれば、前回が問題なしでも必ず見る（変更が、新しい権限の広がりや危険な指示を持ち込みうる）。
