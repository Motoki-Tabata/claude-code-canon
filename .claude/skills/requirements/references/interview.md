# ヒアリングの進め方

ヒアリングの目的は、「何を達成したいか」と「何を使ってよいか」を、後工程が判定に使える形で固めることである。自明な質問は避け、判断が割れるところ（エッジケース・トレードオフ）に踏み込む。AskUserQuestion で要点を掘り下げる。

## 冒頭: 調査サマリを見せてモードを決めてもらう

調査①（existing・profile）の結果を要約して示し、新規作成か既存改修かをユーザーに選んでもらう。既存カスタマイズがあれば件数と層の内訳を示す。profile に `learning_history` があれば、その要点（既知の落とし穴・過去の申し送り）も示す。要件が、対象が過去に踏んだ問題を繰り返さないようにするためである。

## 質問のカテゴリ（この順で聞く）

1. **モード確認**: 新規作成か既存改修か（既存カスタマイズの有無を示したうえで）。
2. **対象と目的**: どのプロジェクトに、何を達成するカスタマイズを入れたいか。
3. **必要機能の兆候**: 常時必要な規約（L1）・繰り返す手順（L2）・専門への委譲（L3）・イベントでの自動化や外部連携（L4）・配布（L5）。機能の選定そのものは design の仕事なので、ここでは兆候を拾うだけにする。
4. **制約（constraints）**: シークレットの扱い・hooks／mcp／plugins／experimental の使用可否・組織ポリシー。機能選定の探索空間を先に絞る入力になる。禁止と「今は使っていない」は別なので、禁止なのかを必ず確かめる。
   - 既存改修で「対象が既にその機能を使っていて、維持したいが新規には足さない」と言われたら、`allowed: false` にしない。`allowed: false` は「生成物のどこにも現れてはならない」を意味し、既存の keep 対象がその機能を使っているだけで機械的に止まる。`allowed: true` にして `reason` に「既存を維持・新規追加なし」と書く。この区別をユーザーに確かめる。
5. **要件ごとの強度**: 各要件が advisory（CLAUDE.md の助言）・deterministic（Hooks による確実な実行）・enforced（permissions による強制）のどれを要るか。deterministic を望むのに hooks を禁止している、のような衝突を見つける材料になる。
6. **検証基準**: 成功をどう確かめるか。後で spec の受入基準の出典になる。

## 衝突の扱い

`conflicts` に載せるのは、**未解消の衝突だけ**（`constraints` の実在キーが `allowed: false` で、当該の要件を禁止しているもの）。ヒアリング中に解消した衝突の経緯、`constraints` に由来しない方針の相違、配置後の手作業メモは `conflicts` に入れず、requirements.md の散文の小節に書く。`conflicts` は `requirement` が確定要件の実在 id、`constraint` が `constraints` の実在キーを指している必要があり、機械が照合する。

## AskUserQuestion の使い方

- preview が表示されない環境がある。判断材料は質問文か直前の本文に書き、「右の」「上のプレビューの」のように位置で参照しない。
- 選択肢は互いに排他的にし、推奨があれば先頭に置く。

## ユーザーが過去のセッション履歴（transcript）の分析を要件の材料に指定したとき

1. 先に `npm run tokens -- <session-id>` で区分別の消費を出し、分析で読む範囲を絞る。
2. 分析は Explore（または general-purpose）に委ね、`model: "sonnet"` を明示する（定義ファイルを持たないので、明示しないと親のモデルを継承して高くつく）。読み取り専用で、ファイルを書かないことを指示する。
3. 分析結果は、応答本文を**逐語で** `work/<ts>/session-analysis-<名前>.md` に保存する（要約・整形しない）。

## 合意したら

[requirements-template.md](requirements-template.md) の書式で `work/<ts>/requirements.md` を書き、ユーザーに承認（P1）を求める。承認を得たら handoff.md の承認行に記録する。
