# ゲート・テスト・CLI 実装規律

`gates/` は最適化対象外の不変土台（機能Y 不可侵）。検出器・ガード・ツールを書き足す／直すときは
次を守る。

- **vacuous pass を最優先で疑う**。検出0件は「検出成功」の証拠にならない。故意の違反を注入して
  検出器が実際に発火することを示してから「検出できる」と言う。ライブ環境でしか踏まない組み合わせ
  （保護パス＋stderr リダイレクト等）は fixture の素振りだけでは見つからない。
- **開示・除外・許可の正規表現は、判定対象の識別子自身への自己一致を疑う**（`EXPERIMENTAL_AGENT_TEAMS`
  が `EXPERIMENTAL` を含む、`WRITE_OP_RE` が `2>&1` の `>` に誤反応する、等）。テストは検出対象の
  識別子が判定条件の語彙と字面上重なるケースを明示的に踏む。
- **保護パス判定は「出現」でなく「宛先」で行う**。「コマンド文字列のどこかに書込操作がある」×
  「どこかに保護パス文字列がある」という出現ベースの AND は、両者の位置関係を見ないため、
  データ（heredoc 本文・クォート文字列）・読取コマンドの引数（`grep docs/ .claude/`）・fd
  リダイレクト（`2>/dev/null`）に保護パス文字列がたまたま出現しただけの sanctioned な操作を
  誤って deny する（write-scope-guard 系3ガード・`gates/lib/shell-write.js` の
  `analyzeShellWrite()`・2026-09-04 ライブ run `20260903_091044` で実測）。書込宛先を具体的に
  同定できる構文はリポジトリ相対パスへ正規化してから保護ディレクトリと突合し、同定できない
  構文（`node -e`・`bash -c`・`$VAR` 等）だけ従来どおりの出現ベース広域スキャンへフォール
  バックする。緩めた分は「宛先を静的に確定できた場合に限る」という条件で担保し、検出力を
  落とさないことを実測（意図的な検出無効化での赤化・vacuous pass 排除）で示す。
  **`node -e` はさらにスクリプト本文まで見る**（`gates/lib/shell-write.js` の
  `stripReadOnlyNodeEval()`）——本文に書込 API も `child_process` も現れず、かつ引用符で
  閉じていて終端が静的に確定できる呼出しだけを読取専用と見なし、判定材料から外す。出現ベースの
  ままだと `readFileSync` しかしていない JSON 構文検査まで、コマンド文字列に保護パス文字列が
  出現するだけで deny され、保守のたびに書き方の試行錯誤が発生する（ライブ run
  `20260909_003820` で実測）。緩めた側の対として、`node -e` 経由の実書込・`child_process` 委譲・
  引用で閉じていない本文が引き続き deny されることを `tests/write_scope_guard.test.js` が
  故意の違反注入で示す。
- **「一覧に出すな」型の規定は、文字列の出現でなく出現位置で判定する**。`readme.includes(name)` の
  ような全文部分文字列検査は、契約が禁じている「利用者向け一覧への掲載」でなく「本文への出現」を
  禁じてしまい、契約が同時に推奨する書き方（詳細設計書 §12.4「「内部で参照される知識」に留める」）を
  充足不可能にする（G10・`gates/lib/readme-listing.js`・ライブ run `20260903_091044` で実測。生成
  README が §12.4 の指示どおり書いた節でブロックされ、hook 実体のパスを README から消す是正を
  強いられた）。判定は「見出し行・表の第1セル・箇条書きの先頭区分」という**一覧項目の位置**と、
  `/名前` という**起動方法の案内**の2軸に絞り、散文とパス表記（前後が `/` の出現）は対象外にする。
  上の「出現でなく宛先」（write-scope-guard）と同型。緩めた分は、狭めていない側（一覧への注入・
  `/名前` の出現）が現に発火することを故意の違反注入で示す。
- **ゲートの冒頭コメントが掲げる検査項目は、項目ごとに実装の有無を追跡する**。G10 は「起動方式の
  正典整合（§12.4 導出ルール一致）」を冒頭コメントと詳細設計書 §11.2 の両方で掲げながら、
  `deriveLaunchMethod()` の戻り値のうち `listed` しか使わず `method` を捨てていた——**宣言した検査が
  一度も走っていない** vacuous pass。未実装項目は `NOT_YET` へ明示的に積む（`gates/gate-manifest.js`
  が回収する）か、実装する。コメントに書いてあることを実装の証拠にしない。
- **禁止/許可リストは代表例でなく能力（capability）で書く**。「Bash」でなく「コマンド実行系ツール」、
  「echo >」でなく「書込操作」。正典の全集合を実際に走査してから網羅性を確かめる。
- **「ロジックが正しい」と「hook として発火する」は別の検証**。settings.json の自己検証は原理的に
  不可能——npm test が緑でも配線は死にうる。カナリア（run 内）と配線テスト（npm test）は代替でなく
  補完であり両方要る。
- **同じ判定ロジック（除外リスト・正規表現・分類器）を複数箇所へ複製しない**。`gates/g12_output_perfile.js`
  の `KNOWN_NON_SCHEMA`／`tools/promote.js`／`tests/self_application.test.js` へ独立に複製した
  除外判定が波及漏れを2度起こした。共有モジュール（`gates/lib/*.js`）へ集約し import する。同一ファイル
  内の姉妹関数（`walkMd`/`walkMdFs` のような対）も見落としやすいので同様に確認する。
- **JSDoc/ブロックコメント中に `*/` が連続する表記を書かない**（`output/*/` や `candidate-*/` 等の
  ワイルドカードパス表記）。`*/` はコメント終端トークンとして字句解析される。`<...>` プレースホルダ
  表記に置き換える。新規ファイルは `node --check <file>` を単体で通す。
- **`isMainModule` ガードの無い実行専用スクリプトから named export を追加するとき**、import される
  だけで実行・書込・`process.exit` が起きないか確認する。追加のその場で `if (isMainModule(...))` を
  是非付ける。
- **ディレクトリを歩いて特定パターンのファイルを集める処理は `readdirSync` 手書き再帰でなく
  `git ls-files` ベースにする**。git worktree・退避ディレクトリ等の追跡外の物理実在物を誤って
  拾わないため。
- **保守編集が `sanctioned ツリー外` 等で deny されたら、まず `work/.session-ts`（および
  `.canon-update-ts`・`.self-optim`）の残置を疑う**。テスト・スモークの中断は run in-flight の
  誤判定を残しうる。
- テスト赤に遭遇したら、`git stash` で自分の変更を退避しても再現するかを先に確かめる
  （変更起因か環境起因かの切り分け）。ガードテストは実 `work/`・`output/` を変更するため
  `--test-concurrency=1` で直列実行し、実 ts の日付部分をテストファイル間で重複させない。
- **複製排除はテスト側にも及ぶ**。パス解決・sentinel 退避復元・fixture 生成は `tests/helpers/*`
  から import する（`gates/lib/*.js` を個別に再導出しない）。ただしガード呼出しは子プロセス起動
  （`tests/helpers/hook.js`）のまま保つ——in-process import に変えると「ロジックが正しい」と
  「hook として発火する」の区別が消える。
- 実 `work/<ts>`・`output/<ts>` を触るテストの ts は `tests/helpers/ts.js` の `tsFor`/`tsSeq` 経由で
  発行し、`TS_NAMESPACES` に他と重複しない8桁日付を登録する（`tests/ts_namespace.test.js` が重複・
  直書き・レジストリの腐りを機械検査する）。
- 複数のガードテストファイルをまとめて自分で `node --test` に渡すときは、実 `work`/`output`・
  実sentinelに触れる限り必ず `--test-concurrency=1` を付ける（`npm test` 自体は固定済みで安全）。
- **テスト赤が「件数0／ディレクトリが空」なら、まず入力（fixture・コーパス）の実在を疑う**。
  追跡外の資産に依存するテストは、不在時に理由と復元手順を書いた明示スキップにする。
- **1ゲートの false positive を根拠に unblock しない**。残りのゲートを個別に import して実測し、
  全て clean であることを確認したうえで、ユーザーへ選択肢として提示（AskUserQuestion）して
  承認を得てからオーバーライドする。実施内容はマーカーの meta とログの両方に残す。
- **judge とラベルの不一致は正典・契約の一次ソースを grep して裁定する**。「ラベルが正解」も
  「judge が正しい」も前提にしない。judge を直すときはコーパスでなく契約（`quality-checklist`
  と該当 `eval-*` の両方）を直し、改訂後に両側のケースを再収録して片側改善で逆側が壊れて
  いないかを確認する。満点は「コーパスが甘い」証拠にもなる。
- **「生成物を隔離する」設計を入れたら、隔離物の鮮度検出も同時に設計する**。隔離は「更新されない」
  ことも意味し、放置すると「古いまま気づかれない」新しい穴になる。鮮度判定は disposition で
  層別する——keep の差分は異常、modify/新規の差分は当然（`tools/promote.js` の乖離検出）。
- **終端マーカーはガードの有効条件そのもの**（`gates/lib/run.js` の `currentRunTs()`）。工程を
  巻き戻す設計を入れるときは「再検査（ゲートバッチ）が走るか」と「ガードが武装しているか」を
  別々に確かめる——両方ともマーカーの存在に懸かっているため、片方だけ効く phase 別キー
  （`generation.round2` 等）のような解は、検査が緑になるのにガードが沈黙したまま、という
  現状より悪い状態を作りうる（`tools/reopen.js`・基本設計書 §4.5 巻き戻し）。
