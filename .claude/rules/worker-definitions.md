# ワーカー定義・hooks 配線の取り扱い規律

- **hook の `command` にシェル構文（引用符・スペース・`${...}` 展開）を書くなら `args` フィールドを
  付けない**。`args`（空配列 `[]` を含む）が存在すると exec 形式になり `command` は単一実行ファイル
  名として扱われ、hook が黙って落ちる（silent allow）。node スクリプトは shell form か exec form の
  どちらかに統一し混在させない。
- **決定論ゲート（`gates/*.js`）の判定基準を変更したら、それを平易な言葉で説明するワーカー定義の
  該当箇所（表・箇条書き）を同じ変更に含める**。ゲートは機械が読み、ワーカー定義は LLM サブ
  エージェントと人間が読む——片方だけ直すと、読者の違う側が古い理解のまま動き続ける。契約変更の
  たびに旧い語彙をワーカー定義側へ横断grepし、追従していない箇所を洗い出す。
- **サブエージェントへ「正典フォーマットに従え」とだけ指示しない**。値の語彙契約（裸パス vs
  バッククォート引用、`[]` と自然文「なし」の不一致、複数参照を1エントリへ圧縮しない等）は
  構文だけでは伝わらない。`fixtures/sample-repos/*/expected-work/` の実例を直接参照させる。
- **サブエージェント応答を `work/<ts>/` へ永続化する前に、対応するパーサへ実際に通す**。応答を
  そのまま信用して転記しない。「機械的に直列化せよ」と指示したワーカーの出力も、指示との一字一句の
  一致を検証する——機械係が機械的とは限らない。大量データを手作業で書き写すときは書き終えた直後に
  件数を数え直すか、パーサをその場で実行して異常（解決率の急落等）を検知する。
- **応答を要約・整形・重複除去せず逐語で書き出す**。下流のパーサが重複を吸収する設計なら、転記側で
  先回りして「整理」しない——整理しようとすること自体がヒューマンエラーの経路になる。
- **自己参照構造（keep 対象が claude-canon 自身のインフラである等）で「絶対条件」型ゲートが機械的に
  発火したら、まず「ゲートが今の工程で判定材料を持たないだけで後工程なら判定できる」のか
  「意味論的に本当に不確定」なのかを切り分ける**。前者なら人間裁定を毎回繰り返すのでなく、宣言
  （design 段階）＋後工程での実照合（generation 段階）のペアで機構的に解く。宣言だけを見て判定する
  コードパスを単独では許可条件にしない。同じ理由の human override が2回目に発生した時点で、
  1回性の例外か構造的トラップかを再検討する。
- **`constraints.<capability>.allowed:false` は「新規も既存も問わず一切存在してはならない」という
  絶対不在の意味**。対象が既にその機能を正当に使用しているなら `allowed:true` + reason（既存維持・
  新規禁止の明記）を使う。
- **配下を spawn するコーディネータ（`Agent` ツールを持つワーカー）は、ワーカーの結果回収・集約・
  永続化・完了リクエストの書込を同一 turn で終える**。「配下の完了を待つ」と述べて turn を終えると、
  `.requests/<stage>` が書かれないまま SubagentStop が発火し、ゲートは検査対象を見つけられず沈黙
  して通す（実測: run 20260903_091044 で investigator・eval-reviewer が各1回・詳細設計書 §11.5）。
  成果物の実在を自分で確認してから完了リクエストを書くこと、確認できないなら完了リクエストを
  書かずにその旨を報告することをコーディネータ定義に明記する。
